# 厦大体育健身房后台读取可行性报告

> 历史说明：本文记录 2026-11-02 的独立 HTTP 认证评估。2026-11-05 已改为
> 通过 Windows UI Automation 读取已登录小程序页面，当前实现与结论请以
> `BACKGROUND_FEASIBILITY.md`、`DATA_SOURCE_REPORT.md` 和
> `TEST_REPORT.md` 为准。

评估日期：2026-11-02
范围：翔安校区爱秋体育馆健身房，`stadium_id=16`，
`category_id=8`

## 结论摘要

**技术上可建立独立的只读 HTTP 客户端，但当前版本还不能在无授权条件下
稳定取得真实场馆数据。**

接口本身可以从公开 H5 中识别，但匿名调用
`getStadiumDetails` 返回“登录信息失效”。因此当前可交付的是：

- 完整接口分析；
- 可替换认证适配器；
- 只读数据读取层；
- PySide6 桌面界面；
- 登录失效识别和结构化异常；
- 后续接入正式认证的工程基础。

不能把当前接口视为已获准、公开、长期稳定的第三方 API。

## 1. 能否不打开微信界面独立读取场馆数据？

### 技术结论

**在具备有效、获准的认证适配器时可以；当前匿名状态下不可以。**

原因：

1. 业务接口是标准 HTTPS 表单 POST，不依赖微信客户端负责渲染。
2. 匿名请求可以到达 API，但服务端业务层返回登录失效。
3. 当前无法从公开匿名响应中获得 `venue_id` 和 `user_range`。
4. 不获取这两个字段，就不能可靠构造健身房的 `getInterval` 请求。

实现层已通过 `AuthenticationAdapter` 预留认证注入点。适配器可由校方
提供的 Token、OAuth、客户端证书或其他正式机制实现。

### 限制

在没有正式授权时，即使技术上能够复用某个浏览器会话，也不建议将其作为
“独立后台 API”。这会产生账号安全、会话稳定性、服务条款和数据合规风险。

## 2. 是否依赖微信登录状态？

**当前接口依赖服务端认可的登录会话，是否必须由微信直接产生尚未得到
官方文档确认。**

源码证据：

- 请求封装会使用浏览器 Cookie 会话。
- 新版模式还要求 WebView bridge 返回 `h5_token`。
- `getStadiumDetails` 的匿名实际响应明确表示登录失效。
- `getInterval`、`getVenueConfig` 和 `addOrder` 位于同一业务链路。

在获得有效认证之前，本项目不能证明“普通 HTTP 客户端只靠一个静态
Token 就能长期访问”。

## 3. 登录会话有效期如何验证？

当前没有发现独立的 `tokenInfo` 或 `sessionExpire` 接口。建议通过一次
低频、只读的 `getStadiumDetails(stadium_id=16)` 探测：

| 结果 | 判定 |
|---|---|
| `status == 1` 且 `data` 可解析 | 会话当前有效 |
| `status == -1` | 会话无效或需要登录 |
| `status == 0` 且 `info` 含“登录/失效” | 会话无效 |
| HTTP 超时或网络错误 | 不能据此判定会话失效，应重试并记录网络状态 |
| HTTP 200 但非 JSON | 服务异常或网关变化 |

建议最低频率：

- 人工刷新间隔不少于 60 秒。
- 自动轮询间隔由校方或接口维护方明确后决定。
- 本项目默认两次 HTTP 请求之间至少间隔 1 秒，且界面不自动轮询。

会话续期不能靠猜测或重放登录请求实现。必须由认证适配器提供正式刷新
流程，且刷新凭据不得写入源码、普通日志或 Git 仓库。

## 4. 是否有正式授权的 API 使用方式？

**目前没有发现。**

本次检查只看到公开可访问的 H5 前端和内部业务路由，没有发现：

- 公开 API 文档；
- OpenAPI/Swagger 定义；
- 第三方开发者申请入口；
- 明确的 API 使用许可；
- 接口版本和稳定性承诺。

所以“接口存在”不等于“第三方后台程序获准使用”。正式集成前应联系
厦门大学体育系统维护方，确认以下内容：

1. 是否允许非微信客户端访问；
2. 可使用的认证方式；
3. 数据字段和调用频率限制；
4. 是否允许持久化数据；
5. 接口变更通知和问题反馈渠道。

## 5. 是否有官方支持的验证码处理方式？

**没有发现。**

当前源码显示：

- 验证码以图片形式返回；
- 用户需要在 H5 页面输入；
- `addOrder` 请求携带用户输入值。

本项目没有实现验证码下载、自动识别、绕过或伪造。

如果未来需要自动预约，可接受的方案应是：

- 校方提供机器可用的正式鉴权/确认机制；或
- 保留人工输入验证码的桌面交互；或
- 校方明确允许的受控服务账号方案。

2. 有效的 `venue_id`、`user_range` 获取流程。
3. 对完整成功响应的合规验证和字段契约确认。
4. 接口版本、限流和维护窗口说明。
5. 凭据安全存储方案，例如 Windows Credential Manager 或受控服务端
   Secret Store。

7. 故障通知和人工接管流程。

### 工程上已具备

- 独立异常类型。
- 会话认证替换点。
- 日期、时段、场地、容量、已选人数、剩余名额和状态解析。
- 只读请求节流。
- 桌面手动刷新、状态显示和日志查看。
- 滚动日志文件。

## 7. Windows 后台运行评估

### Windows 任务计划程序

优点：

- 内置于 Windows；
- 支持开机、登录、定时和事件触发；
- 可配置失败重启和独立工作目录；
- 适合低频只读刷新任务。

注意事项：

- “无论用户是否登录都运行”通常要求保存任务运行账户凭据；
- 若认证依赖交互式 Windows 用户会话，非交互任务可能无法复用登录态；
- 启动前应检查单实例锁，避免多个进程同时刷新。

### WakeToRun

任务是 Windows 任务计划程序选项，用于请求系统从睡眠/休眠状态唤醒。

限制：

- 依赖主板、电源策略和网卡支持；
- 不能从完全关机状态启动；
- 可能唤醒整台设备，应谨慎设置；
- 唤醒后仍需验证网络和认证会话；
- 不应因一次失败连续高频重试。

建议：

- 只在确有实时性要求时开启；
- 设置合理的执行时间窗口；
- 任务执行后允许系统重新睡眠；
- 记录每次唤醒和任务结果，便于审计。

### Python 后台服务

当前阶段更适合“任务计划程序 + 单次 Python 命令”，而不是常驻 Windows
服务。原因是：

- 认证可能需要用户交互；
- GUI 和只读批处理可以共用同一 reader；
- 单次任务更容易控制频率、超时和故障范围；
- 后续确认认证机制后，再抽象为 Windows Service。

如果改成常驻服务，应增加：

- 单实例锁；
- 任务队列；
- 指数退避；
- 会话过期熔断；
- 健康检查；
- 优雅停止。

### 日志持久化

桌面程序已经使用 `RotatingFileHandler`：

- 文件：`logs/app.log`
- 单文件上限：1,000,000 字节
- 保留 5 个历史文件
- UTF-8 编码

日志仅记录操作结果、异常类型和数量，不记录 Cookie、Token、密码或请求
认证头。

### 异常恢复

建议策略：

1. 网络错误：有限次数重试，指数退避。
2. 认证失效：停止重试，提示重新认证。
3. JSON 结构变化：停止解析并告警，不猜测字段。
4. 服务端 `status=0/-1`：按业务失败处理。
5. UI 线程不得执行网络请求，避免窗口无响应。

当前实现已用独立工作线程执行刷新，并且只有在手动点击时才发起请求。

### 登录会话有效性检查

推荐把会话检查与业务读取合并为一次低频 `getStadiumDetails` 请求，避免
额外探测增加服务负担。

状态字段判断规则见第 3 节。网络异常不能直接等同于会话失效。
