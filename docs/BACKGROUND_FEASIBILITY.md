# 后台运行可行性判断

更新日期：2026-11-05

## 1. 已验证事实

1. Windows UI Automation 可以从已登录的“厦大体育”小程序读取页面文字。
2. `MiniProgramUiBridge.exe` 在用户交互桌面成功读取翔安校区健身房详情。
3. PySide6“刷新数据”通过同一桥程序成功显示 `mini_program_live` 数据。
4. 一次真实只读后台运行返回：

   ```text
   status = NO_NEW_AVAILABILITY
   exit_code = 0
   matched_count = 2
   notification_count = 0
   ```

5. 当前两天页面状态均为“暂无”，没有把不可预约误报为空位。
6. Windows 计划任务可手动运行且结果码为 `0`，但本机系统会把它持续标记回
   `Disabled`，因此不作为主要方案。
7. 已改用 Windows 启动文件夹中的 `厦大健身房空位监控.lnk`，登录后启动
   `app.py --daemon` 常驻工作者。
8. 守护进程实际启动并完成首轮读取；5 分钟后第二轮自动执行，均返回
   `NO_NEW_AVAILABILITY`。
9. Bark Key 已存在于 Windows Credential Manager；本报告不读取或显示 Key。

## 2. 逐项回答

### 2.1 微信最小化时能否读取？

**可以，已实际验证。**

2026-11-06 14:40:35，在“厦大体育”窗口保持最小化的情况下执行完整读取，
成功返回：

```text
data_source = mini_program_live
page_kind = detail
dates = 2026-11-06, 2026-11-07
parse_success = true
```

读取后窗口仍保持最小化。纯 `read` 操作不会调用 `SetForegroundWindow`；
只有日期出现“预定”、需要进入选场页读取具体时间段时，程序才可能需要
激活窗口执行点击。

### 2.2 微信退出后能否读取？

**不能。**

当前读取来源就是 `WeChatAppEx.exe` 中标题为“厦大体育”的窗口。窗口不存在时
会返回 `miniprogram_window_not_found`，不会改用 Cookie 或匿名 HTTP。

### 2.3 Windows 锁屏时能否读取？

**可以，已实际验证。**

2026-11-06 17:27:59 执行真实锁屏读取，读取前后均为：

```text
workstation_locked = true
logon_ui_running = true
WeChatAppEx running = true
"厦大体育" window minimized = true
reader exit code = 0
data_source = mini_program_live
parse_success = true
```

锁屏状态下成功读取 2026-11-06 和 2026-11-07 两个日期。这里只覆盖“锁屏但
电脑仍运行”；睡眠或休眠会暂停进程，不能继续监控。

### 2.4 是否依赖用户交互会话？

**依赖 Windows 当前用户的交互会话。**

计划任务运行时不需要用户点击，但需要：

- 用户已登录 Windows；
- 微信未退出；
- 小程序窗口存在；
- 小程序内部登录有效。

用户注销后任务无法读取。锁屏与注销不是同一状态。

### 2.5 是否需要微信客户端常驻？

**需要。**

这是 UI Automation 方案，不共享微信 Cookie。微信或小程序关闭后就没有可读
页面。只有校方提供正式 API/Token 时，才可能移除对微信客户端的依赖。

### 2.6 能否通过 Windows 任务计划程序运行？

**程序可以被任务计划程序执行，但本机无法稳定保持任务启用。**

手动启动实测：

```text
TaskName = XMU Gym Monitor
LastTaskResult = 0
Interval = 5 minutes
LogonType = InteractiveToken
WakeToRun = true
```

但管理员将 `Settings.Enabled` 改为 `true` 后，Windows 很快又改回
`Disabled`。因此已删除该任务，避免和常驻监控重复。

当前实际入口：

```text
启动文件夹\厦大健身房空位监控.lnk
  -> tools\LaunchMonitorDaemon.exe
  -> pythonw.exe app.py --daemon
```

### 2.7 登录失效后能否自动恢复？

**可以恢复的情况：**

- 小程序窗口仍在，但页面停在首页或场馆列表：程序会自动只读导航到场馆详情。
- 用户重新登录小程序后：常驻守护进程的下一轮检查会自动继续读取。
- 页面短暂未加载：下一轮任务会重新尝试。

**不能安全恢复的情况：**

- 微信窗口被关闭；
- 微信退出或 Windows 用户注销；
- 小程序登录过期且需要人工重新认证；
- 微信要求验证码或扫码确认。

程序不会保存统一身份认证密码，也不会自动处理验证码。登录失效时会发送冷却
后的 Bark 异常通知；在用户重新登录前，不会发送伪造的空位通知。

### 2.8 是否需要重新设计认证适配器？

**当前读取链路不需要复制 Cookie 的认证适配器。**

它使用本地 UI Automation 读取用户已经有权查看的页面。若未来要彻底脱离微信，
仍需要校方正式支持的 API 或 Token；但那不是当前版本的必要条件。

## 3. 当前后台行为

| 事件 | 行为 |
|---|---|
| 小程序在首页 | 只读点击“场馆预约”和“翔安校区健身房” |
| 详情页显示“暂无” | 记录 `unavailable`，不通知空位 |
| 详情页显示“预定” | 发送“预约入口开放”通知 |
| 选场页可解析名额 | 按容量分数计算并去重通知 |
| 小程序窗口不存在 | 记录失败，可按冷却发送异常通知 |
| 小程序登录失效 | 标记 `AUTH_REQUIRED`，停止空位通知 |
| 网络/UI 暂时失败 | 下一轮重试，不自动把缓存当实时数据 |
| 发现可预约状态 | SQLite 去重、冷却控制、Bark 推送 |

## 4. 可靠性边界

不能承诺“登录永远不会断”。能保证的是：

1. 断线会被识别，不会静默当成无空位；
2. 不会把历史缓存伪装成实时页面；
3. 不会高频轰炸接口或 UI；
4. 不会处理验证码或自动提交预约；
5. 用户重新登录后，常驻守护进程会自动恢复读取。

## 5. 最终判断

当前版本适合：

- Windows 保持登录、微信和小程序常驻的个人电脑；
- 每 5 分钟检查翔安校区健身房的可见预约状态；
- 通过 Bark 接收预约入口或明确空位提醒；
- 在登录失效时接收异常提醒并人工恢复。

当前版本不适合：

- Windows 用户注销后的无人值守；
- 微信完全退出后的后台读取；
- 绕过登录、验证码或服务端访问控制；
- 自动提交预约订单。
